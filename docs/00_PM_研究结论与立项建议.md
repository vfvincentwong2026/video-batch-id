## 四、PM 立项判断

### 4.1 最大风险排序

1. **算力风险（决定性）**：没有 GPU，一切"本地生成"承诺都无法兑现。MVP 必须把生成层抽象成 **Provider 接口**（本地 ComfyUI / 云 GPU / API 三态可切换），先跑通 API 或云 GPU 形态。
2. **依赖幻觉风险**：README 架构里的 pixhub、reel-kit 两个组件查无可靠实体，直接按 README 搭会踩空。替换为自研轻量网关 + html-video/Remotion。
3. **成本模型风险**：README 假设 $0.15/条。本地 Wan 2.2 单条约 0.1 GPU·时（4090 约 $0.089/时 → ~$0.01/条 + 电）；API 路线（如可灵/即梦/Seedance）约 $0.1–0.5/条。差异 10–50 倍，必须在 MVP 前用真实报价重算成本档。
4. **去重阈值风险**：TikTok/Shopee 判重阈值是黑盒，README 的 0.65 是假设值。需要"投放回传真实数据 → 校准阈值"的闭环，这本质是 v0.6 知识层的核心价值。

### 4.2 MVP 范围裁决（对 README v0.1 的修正）

**做（v0.1 真实范围）**：
- 工作台 Web（Next.js）：上传参考 → 解析结果确认 → 变量矩阵 → 生成队列 → 审核网格 → 谱系视图
- 参考解析：VLM API 路线优先（不上本地 7B VLM，省 50GB 权重下载与显存），Whisper/转录可用 API 或本地轻量模型
- 变量矩阵 v1：**只做"视觉 + 文案"两维**（README 六维全做会把 v0.1 拖到三个月）
- 生成 Provider 抽象 + 单条生成链路打通
- 谱系 v1：Master → 变体树 + 入库，先不做价值榜

**缓（挪到 v0.2+）**：双守卫全量（v0.1 只保留真守卫中的 CLIP 相似度单指标）、人物/节奏/音频变量、TTS、Tunnel 公网入口、D1（本地 SQLite 即可）。

### 4.3 三个立项方案（请选一个）

| | 方案 A：API 优先 | 方案 B：云 GPU 优先 | 方案 C：骨架先行 |
|---|---|---|---|
| 思路 | 生成层全走第三方视频 API，本机只跑编排/守卫/谱系 | 租云 GPU（RunPod/AutoDL，~$0.3–0.9/时）跑 ComfyUI + Wan 2.2 | 先把工作台+解析+矩阵+谱系搭起来，生成按钮接 mock provider |
| 优点 | 最快出真片；本机零负担；成本可预测 | 单条成本最低（~$0.01/条）；完全自托管，契合 README 愿景 | 一周内看到完整产品；生成层随时换真 provider；风险最小 |
| 缺点 | 单条成本高 10–50 倍；依赖第三方额度 | 运维重；模型下载 50GB；网络（国内→HF）有摩擦 | 前期产出是"假视频"，演示价值有限 |
| 适合 | 急着给客户/卖家演示真实效果 | 确定长期自用、量大 | 先把产品骨架和团队流程立住 |

**PM 建议：方案 C 打底 + 第一周结束后并行启动 A 的一条真实 provider（如可灵/即梦/Seedance API）**。理由：README 自己也说"组装，而非重造"，编排层的代码在三种算力路线下 100% 复用；先立骨架可以让后续任何算力决策都成为"换插件"而不是"返工"。
